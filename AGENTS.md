# AGENTS.md

Instructions for AI agents (and humans) working in this repository. `CLAUDE.md` points here; this is the single source.

## Where things are written down

What the product does, the env vars, and how to run, test and deploy it: `README.md`. Do not restate any of that here.

Specs and plans, read before changing anything:

- `docs/prd.md`: the original brief. Requirements come from here.
- `docs/sessions.md`: the build plan, session by session, with the architecture, data model and conventions.
- `docs/tech-stack.md`: stack, pinned versions, per-app conventions, and what is deliberately excluded.
- `docs/phase/`: per-phase implementation plans.
- `docs/test-cases.md`: product-level test cases.

## Commands

The ones you need day to day are in `README.md`. Beyond those: `npm run db:generate -w backend` after touching `schema.prisma`, because the client is gitignored; `npm run db:status -w backend` to check a branch is migrated; `npm run db:studio -w backend` to look at rows. Narrow a run while iterating (`npm test -w backend -- action-runner`) instead of running both suites.

Node 24 (`.nvmrc`; run `nvm use`). npm workspaces, no Turborepo. Every command runs from the repository root.

## Conventions

Backend:

- All SQL and Prisma calls live in `*.repository.ts`. Services hold the logic, controllers stay thin.
- Services throw domain errors from `core/errors/`; a global filter maps them to HTTP. Never throw `HttpException` from a service.
- Env is validated once at boot with zod and fails fast, listing names only, never values.
- Every route requires a valid Neon Auth JWT unless marked `@Public()` (health and webhooks only).
- Users belong to Neon Auth in the `neon_auth` schema. Prisma never migrates that schema.
- Webhook signatures are verified against the raw body, never a re-serialised one.
- Anything a user owns resolves through repo, then installation, then user. Someone else's id gets a 404, not a 403.

Frontend:

- No inline Tailwind utilities in app JSX. Semantic classes with `@apply` in `src/styles/components/*.css`. Tailwind's layered rules lose to shadcn utilities, so keep badge and status colours unlayered.
- Components never call `apiFetch` directly; data goes through `use-*.ts` hooks in the feature folder.
- Parse every `/api/*` response with a zod schema. Validate `import.meta.env` once at startup.
- Only `VITE_*` values reach the browser, and none of them is a secret. App code never touches `localStorage` for tokens; the Neon Auth SDK owns the session.
- Never hand-edit `src/components/ui/`; regenerate with `npx shadcn add <name>`.

Both:

- Comments are short (20 to 30 words) and explain why, not what.
- Add a dependency only when the platform cannot do the job cleanly. See the exclusions in `docs/tech-stack.md`.
- Every feature ships with tests in the same commit series. A fixed bug gets a test that fails without the fix.
- Tests mock Prisma, GitHub, Slack and JWKS. No database and no network in unit tests.

## Invariants you may not break

The behaviour these protect is described in `README.md`. What matters here is where each one lives, so a refactor does not quietly undo it:

- `webhooks/webhook-signature.guard.ts` verifies the signature against the raw body. Never verify a parsed or re-serialised body, and never widen `@Public()`.
- `actions/action-runner.ts` calls `begin()`, which increments `attempts`, before the side effect. Moving that write after the call reintroduces duplicate comments on a mid-flight crash; `AI_NOTES.md` has the history.
- `webhooks/*.repository.ts` writes the delivery and its job in one transaction. `queue/job.repository.ts` owns the claim query; keep the lock fencing when changing it.
- `core/logger/redact.ts` strips secrets from log output. New log lines carry ids, never payloads or tokens.
- Unique constraints in `prisma/schema.prisma` are the guarantee, not the code around them. Do not drop one to make a write easier.

## Git

- Never run `git push` without explicit approval. There is an `ask` rule in `.claude/settings.json`; ask in chat as well.
- Never switch or create branches unasked.
- One commit per logical step, conventional commit messages.
- Never commit `node_modules/`, `.env*` (except `.env.example`), `dist/`, `*.pem`, or generated Prisma output.
- Do not add AI tools as commit co-authors.

## Testing against real GitHub

Use the throwaway repository in `docs/sessions.md` under "Test repository", never a real project repo, and clean up the issues and branches you create. The reviewer-facing walkthrough is in `README.md`.

## Keeping notes

When the AI gets something wrong, or a decision is made, add a line to `docs/ai-log.md` under the current session. `AI_NOTES.md` is condensed from that log.
